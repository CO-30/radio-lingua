## 2026-11-14 音声が勝手に流れる件
- 原因1: 確認作業で使った Claude アプリ内蔵ブラウザのタブ（非表示）が残っていた。タブを閉じて解消。
- 原因2（アプリ側）: AIの準備中に「受信して翻訳」を押すと、準備完了時に自動で受信が始まる。準備に数分かかると、忘れた頃に突然音が出る。
- 修正: 押してから45秒以内に準備が終わり、かつ画面を表示しているときだけ自動で始める。それ以外は「AIの準備ができました。『受信して翻訳』を押すと受信を始めます。」と表示して待つ（src/core/autostart.js、テスト3件追加、全71件・E2E成功）。

## 2026-11-15 日本語読み上げをもっと自然に
- OS標準音声: Natural（Edge）/Premium/拡張版/Google の声を優先、速さ1.15→1.0倍（テスト3件追加）。この Mac の内蔵ブラウザには簡易版（Kyoko・Hattori・O-Ren）しかない。
- 無料のローカル音声合成の候補を比較:
  - Supertonic 3（OpenRAIL-M、商用可・帰属表示・用途制限あり、日本語対応）: fp32 380MB、int8 98MB（soniqo/Supertonic-3-ONNX-INT8）。CI の CPU で速さは実時間の0.43倍（fp32）/0.73倍（int8）で、リアルタイムに間に合う。サンプル: public/samples/tts-eval/
  - piper-plus つくよみちゃん（38MB、OpenJTalkで抑揚◎）: コーパス規約で公開前の作者連絡が必要、ベースモデルの学習データ不明 → 商用前提では保留。
  - Kokoro: 日本語の読み変換が JS版に無く不採用。
- Gemini 3.5 Live Translate（Google、音声→音声の同時通訳、話し方の調子も保つ）: 無料枠あり（データは Google の改善に使われる）、有料枠は約$0.037/分（約330円/時間）。APIキーが必要で公開サイトに埋め込めないため、使うなら「利用者が自分のキーを入れる任意モード」。採用はユーザー判断待ち。
- ユーザー判断: 無料のまま（Gemini は使わない）。A（F2）・B（M1）は良い、C（int8）は聞き取れない → fp32 を採用。
- 実装: 設定「読み上げの声」に端末の声／AI音声（女性・男性）。AI音声は選んだときだけ約400MBを取得（Cache Storage に保存、起動時は取得済みのときだけ準備）。読み上げ専用 Worker（WebGPU→WASM）、文ごとに合成して途切れなく再生、準備中・失敗時は端末の声。規約 第4条の2・CREDITS に Open RAIL-M の用途制限を記載。
- 検証: アプリの実装は公式サンプルと同じ長さ・音量（CI・実モデル、全4文で差0%）。利用者の Mac（2コア Intel・内蔵ブラウザ）で取得〜準備 約80秒、GPU動作。速さは実時間の約3倍かかる（手順8）／約1.3〜2倍（手順4）。主な時間は vector_estimator（1手順 約1秒）。CPU（WASM・単一スレッド）はさらに遅い。
- 対応: 実際の読み上げ時間から手順数を 8→6→5→4 と自動で調整。遅れる端末では設定に「端末の声」への切り替えを案内。
- 残課題: 手順4・5の音質をユーザーが確認中。スマホ実機（メモリ約1GB必要）での動作は未確認。
- ユーザー確認: 手順8・5・4 のどれも聞きやすい → 最初の読み上げの計測で、間に合う手順数（8/6/5/4）へすぐ切り替えるように変更（重い端末では最初から手順4）。
- 実機の通し確認（音量0）: AI音声（女性）＋自動読み上げでデモ6交信・11文をすべてAI音声で読み上げ、取りこぼし・端末の声への切り替えなし。ただし読み上げの合成が字幕のAIとGPUを取り合い、認識時間が 8.5〜21秒（普段の約2倍）に。
- 対応: 読み上げは1文ずつ、字幕の処理（音声認識・翻訳）が空いたときに合成する。字幕の処理が続いても4秒以上は待たせない。
